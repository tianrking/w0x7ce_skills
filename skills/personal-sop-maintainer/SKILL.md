# 個人 SOP 維護

此 Skill 維護個人的規範倉庫，不是背景服務。完成當前任務，再整理有明確共性的流程；避免為一次性操作建立空泛 SOP。

## 找到唯一來源

在本 Skill 目錄執行 `python scripts/locate_sop.py`，取得 SOP 根目錄。來源位於根目錄 `skills/`；安裝副本透過 `.sop-root.json` 指向維護來源。若來源不存在，說明路徑問題，不在宿主工作區另造第二份倉庫。

若目前讀取的是安裝副本，定位後再讀來源的 `skills/personal-sop-maintainer/SKILL.md`，以來源最新已提交流程執行；先以 Git 檢查該來源檔案是否有未提交修改。有修改時保持使用已安裝的已驗證入口，不把工作中的修改當成生效版；維護任務仍可修改來源。不只修改安裝副本。入口描述或定位腳本變更時，須同步已授權的安裝副本，必要時重開宿主工作階段。

閱讀來源根目錄 `rules.md` 和 `shared-rules.md`，再閱讀本次相關領域的 `rules.md`、`state.json`；不要載入全部平台。其餘管理命令從定位結果的來源根目錄執行；用 `python scripts/sop.py status` 查看目前狀態。

## 形成可供人確認的規範

先檢查是否已有適合的領域。新增領域可用 `python scripts/sop.py init <領域名稱>`，再把產生的 `rules.md` 寫成完整、有依據的自然語言規範。已有確認規範則用 `draft <領域名稱>` 建立 `rules.draft.md`，保留生效版本。

區分跨任務偏好、平台要求、單次安排及 AI 建議。只抽象已知共性；未知事項寫成待確認，不杜撰使用者偏好。提供完整草案、檔案連結和必要差異，清楚說明正在等待哪一份版本的確認。不要只讓人批准模糊計畫。

在使用者明確確認前，結束本次規範整理於草案階段，不建立對應子 Skill。若尚有不依賴確認的原任務，可以繼續。不要把沉默、文章認可或「繼續」套用為對未指明草案的確認；對話已有明確版本確認則直接沿用，勿重複索取。

## 確認後建立子 Skill

取得對具體草案的明確確認後，以 `approve <領域名稱> --evidence "確認的原話或可追溯說明"` 記錄指紋。此腳本只記錄證據，不驗證人的身分；禁止自行編造證據或為通過檢查而執行。

以 `check <領域名稱>` 確認生效規範未被更改。在 `<領域>/skills/<skill-name>/SKILL.md` 編寫可重用流程。將根目錄及平台 rules 作為引用來源，不重複整份規範；安裝副本也必須能找到維護來源。僅在需要時新增腳本、參考資料或模板。

遵循目標宿主的 Skill 格式；以必要的實際輸入檢查輸出、路徑及流程。用 `record-skill <領域> <skill-name>` 記錄規範、共用要求及完整 Skill 資源的指紋。修改腳本、模板或其他 Skill 資源後也要重新驗證並記錄。該指令的成功不代表行為測試已完成，回報實際驗證範圍。

已確認規範下的純實作修復可直接改進並驗證；若修改目標、交付或驗收條件，重新形成 rules 草案等待確認。使用者已授權自動同步到登記的安裝目標；確認有效且驗證、版本記錄齊備的子 Skill 會隨同步安裝。未登記的工具、其他帳號或電腦不自動加入；對外發布仍需相應授權。

## 自動保存與本機 Git 提交

使用者已要求將 SOP 的完善自動提交到本機 Git。每次完成有意義的新增或修訂後，檢查本次差異，執行與變更相稱的驗證，再提交；不必為每次本機 commit 重新索取確認。只討論而未修改檔案、內容沒有變更或驗證未通過時，不建立空提交或假稱完成。

開始修改前查看 SOP 來源倉庫的 `git status` 和目前分支，記住既有修改。提交範圍限本次 SOP 的規範、確認記錄、Skill、腳本、測試及必要說明；不要使用無差別的 `git add .`，不要把其他工作或既有暫存內容一併提交。同一檔案混有不屬於本次工作的修改時，先可靠分離再提交。

完成修改後，在 SOP 根目錄執行 `python scripts/finish.py --message "具體變更說明" --files <本次檔案相對路徑...>`。它依序執行結構檢查與測試、限定路徑 commit，再從已提交的 HEAD 同步到登記的目標。明確列出新增、修改及刪除的檔案，不能用目錄或整個倉庫代替。開始前仍須確認同一檔案沒有混入他人變更；程式無法替人判斷修改歸屬。

finish 使用限定路徑的提交方式保留無關暫存內容。不能可靠分離時，回報具體未提交原因，不 reset、stash、覆寫或丟棄使用者的修改。遵循倉庫既有提交檢查，不跳過失敗的 hook；沒有可用提交身分時說明缺少的設定，不自行修改全域身分。

草案可以提交，提交訊息明確標示 draft／待確認；這只保存歷史，不代表使用者已確認，也不解除建立子 Skill 的確認要求。已確認的實作提交說明實際改變的行為。記錄 commit ID，確認提交後本次檔案狀態；沒有額外授權不 push、不發布、不改遠端。

## 自動同步已授權的安裝目標

本機 `.local/installations.json` 只記錄已安裝並獲授權的目標，不提交到 Git。finish 自動同步這些目標，不順便安裝其他工具。同步只發布已提交快照的入口；子 Skill 還須符合已確認 rules、共用要求及完整資源指紋。草案不變成生效規範，待確認的 `rules.draft.md` 不影響舊確認版繼續使用。

過期或失效的已安裝子 Skill 會移至發現目錄外保留，不繼續宣稱它可用；衝突的非本專案 Skill 不覆蓋。同內容重複同步不建立多餘備份。安裝入口指向唯一來源，子入口每次執行前檢查來源的 `check-skill`；來源未記錄變更也會阻止使用。

若 commit 成功但同步失敗，明確回報兩者不同狀態。修正原因後執行 `python scripts/sync.py --apply` 重試，不為同一修改重複建立 commit。有鎖定衝突時先等待另一次操作完成，不擅自移除活躍鎖。已開啟對話可能需要重新讀取 Skill，新描述可能需要重開工作階段；不能宣稱所有對話已立即刷新。

## 回報

說清楚新增或修訂了哪個領域，目前是草案、規範已確認、Skill 待建立、Skill 已建立或需要同步。附可閱讀檔案、驗證結果、本機 commit ID 及各目標同步結果；未提交或未同步時明確說明原因。不把文章圖片和臨時成品放入規範倉庫。
