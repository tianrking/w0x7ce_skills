# 微信公眾號文章

## 規範與定位

來源中的本目錄為 `SKILL_DIR`，專案根目錄是其上三層，領域為 `wechat-official-account`。安裝入口由 `.sop-root.json` 定位唯一來源，不修改安裝副本。

先讀根目錄 `shared-rules.md` 及領域 `rules.md`，再執行根目錄 `scripts/sop.py check-skill wechat-official-account w0x7ce-wechat-official-account`。檢查失敗時回報版本問題，交由維護入口處理，不自行批准新規範。

本 Skill 落實規範，不另維護其完整副本。下列步驟可按現有素材及修訂範圍縮減；不以固定章節、配色或圖數限制文章。

## 寫作與圖文

1. 從當次要求、現有文章及來源確認中心、讀者、文體、需保留內容與交付位置。能合理判斷的細節直接處理；只針對會影響結果的缺失詢問。局部修訂保留已確認部分。
2. 閱讀完整相關來源，核對時效資訊及影響結論的條件；記錄主張對應的來源。翻譯保留原文論點、數字、媒體與限制；補充解說與原文區分。版本比較僅在文章涉及「新增能力」等主張時進行。
3. 先完成完整正文，再選適合題材的題目與導入。以自然繁體表達，按領域 rules 審閱語氣與事實邊界，不把工作日誌當正文。不為某次要求重寫整套風格規範。
4. 依資訊需要選配圖及真實截圖。從實際來源取得官方畫面，保留圖說與來源。生成圖片使用可用的圖像生成工具；不可冒充真實證據。圖表或關係圖核對標註、方向與條件。
5. 每篇交付實際封面檔；依題材生成或選取可使用素材，核對封面短標題與正文一致、縮圖可讀及裁切空間。記錄外部素材來源與必要使用條件。

## 單一正文與排版

以作品資料夾中的 `article.md` 作為正文維護來源，題目為第一行 H1；圖片放 `images/`，使用相對路徑。來源、圖說和必要可編輯圖源隨作品保存，不放入 SOP 倉庫。

從同一版本 Markdown 產生 `body.html` 正文片段：可使用工作環境已提供的 Markdown 轉換工具，或按全文直接製作 HTML。不要臨時下載不明轉換腳本。片段不包含題目 H1、工具列、操作提示或頁面腳本；微信正文樣式使用內嵌 style。保留完整可見引用網址，圖說、配圖與正文內容不丟失。

讀 [references/delivery.md](references/delivery.md)，使用 `scripts/package_article.py` 將已核對的正文片段與 Markdown、圖片封面打包。此工具負責資產內嵌、複製頁與 ZIP，**不負責 Markdown 轉換或證明兩份正文語意相同**；生成片段後必須比對全文，修訂 Markdown 後重新生成片段再打包。

## 驗收與交付

- 按領域 rules 的清單檢查內容、來源、語氣、封面和配圖；逐節比對 Markdown 與渲染正文，特別核對引用、圖說、列表和代碼。
- 在桌面瀏覽器檢查全文與圖片、長網址和表格溢出。實際點擊兩個複製按鈕，核對正文富文字／純文字與題目純文字，工具列不能進入正文。瀏覽器剪貼簿受限時測試內建備援，不以按鈕存在作為功能證明。
- 將來源 ZIP 解壓到不同路徑，檢查 Markdown 相對圖片及封面仍可用；獨立 HTML 在無臨時預覽服務下仍能載入圖片。
- 交付完整 HTML、來源資料夾及 ZIP、獨立封面，附可點擊檔案與實際驗證範圍。若需要，開啟 HTML 供使用者直接複製。
- 平台端測試依當次授權；沒有保存並重新開啟微信草稿，不宣稱格式與圖片已在平台持久化。圖片貼入不被接受時，使用已交付的原圖補入。桌面貼入為主要工作流，不強制手機步驟。

改進流程時使用根維護 Skill。人的目標或交付條件有實質變更，先提出 rules 草案；已確認規範下的實作修復可以驗證、限定 commit，再同步。
