# 微信公眾號文章通用標準
寫作、查證、圖文設計、排版與交付

## 適用範圍

本標準用於不同主題的微信公眾號文章，包括科普、技術解說、研究介紹、產品分析、經驗整理、觀點文章與翻譯。

它定義共同的品質要求，不規定每篇文章使用相同的開頭、章節順序、配色、圖數或敘事套路。單篇文章的案例、品牌、工具與臨時要求，不自動成為其他文章的規則。

預設正文使用繁體中文，自製圖片使用英文；原始截圖保留來源原貌。基本交付包含完整 HTML 排版頁、可搬移的 Markdown 來源資料夾、獨立封面圖片及 ZIP 素材包。

## 一、寫作立場與語氣

使用自然、完整、易讀的繁體中文。語氣中肯、謙遜、專業，尊重讀者的理解能力。

把事情講清楚，讓專業體現在資訊準確、解釋到位與取捨合理。避免居高臨下的說教、誇張宣傳、空泛口號、強行煽情與反覆自我標榜。

直接說明有意義的觀點、行為與結果。少用刻意製造對立的句式、機械轉折、設問自答或沒有內容的結論。

術語按需要使用，首次出現時提供足夠解釋；不為顯得專業堆疊名詞，也不為通俗而抹去關鍵條件。名稱、縮寫與譯法在全文保持一致。

描述優點時交代成立條件，討論限制時說明實際影響。比較以證據、用途與取捨為依據，避免為抬高一方貶低另一方。

不確定性應放在影響判斷的位置，說清楚缺少什麼證據、因此能判斷到哪一步；不以反覆的免責聲明打斷閱讀。

正文面向讀者，不混入製作過程、工具操作、交付狀態或與主題無關的內部溝通。必要的來源、圖像身分與證據限制仍須保留。

## 二、選題、標題與導入

先確認文章要回答什麼問題、提供什麼資訊，以及讀者需要哪些背景。每篇文章應有清楚的中心，相關材料圍繞中心展開。

標題準確、簡潔、具體，與正文實際內容一致。偏好低調、有資訊量的表達，可以呈現值得分析的現象，但不靠誇張語氣製造懸念。

分析類文章的標題可結合「觀察到的現象」與「分析切入點」。若原因尚未證實，使用「排查」「分析」「可能影響」等適當表達，不將候選原因寫成已確定的結論。

避免使用正文無法支持的時間、效果與完整性承諾，例如保證幾分鐘定位、一次解決全部問題，或以單次案例宣稱普遍有效。

導入依題材選擇，可以從問題、事實、場景、觀察、研究結果或必要背景切入，讓讀者盡快理解文章要處理的問題。

不預設要求先介紹經典方案、先寫某個品牌、先作對比或先講個人經歷。只有在背景或比較確實幫助理解時才使用。

不預設添加日期、實測標籤、摘要框或裝飾性背景資訊。若時間、版本或事件背景影響理解，則保留並放在合適位置。

## 三、文章結構與敘事

交付完整、連貫、可直接閱讀的文章，不以摘要、提綱或零散問答代替全文。

結構服務內容。可依文章目的採用解釋、分析、敘事、論證、步驟或原文結構，不強制所有文章套用同一組章節。

重要資訊放在讀者容易找到的位置，背景與細節按理解所需逐步補充。不要把工作過程流水帳當成文章主線。

每段發展一個主要意思，段落之間有清楚的邏輯關係。小標幫助閱讀，但不要切得過碎；條列與表格用於真正適合並列或比較的資訊。

技術或故障分析應讓讀者看懂觀察如何支持判斷：現象說明了什麼、仍不能排除什麼，以及下一步測試能縮小哪些可能性。不要只羅列疑似原因，缺少判斷方法。

例子用來解釋觀點，不能代替論證，也不能把某次案例的條件推廣成普遍結論。示例、真實案例與建議測試應明確區分。

案例可以保留問題、比較條件、關鍵改動與結果，讓敘事有具體依據；與理解無關的專案背景不必展開。

結尾可以停在已充分展開的觀點、實際含義、後續驗證或仍待解答的問題，不強加口號式升華，也不機械地重複全文。

## 四、資料、來源、計算與事實邊界

### 來源與證據

優先使用與主題直接相關、可追溯的原始或權威材料。數字、引文、日期、版本、名稱與重要結論應有依據。

涉及規格、標準或介面時，優先查閱對應的規格書、標準文件、官方文件或原始程式碼。二手文章可以補充理解，不代替關鍵原始依據。

區分下列資訊：

- 來源明確陳述的事實或規格。
- 案例中實際觀察、量測或回報的結果。
- 作者根據材料提出的解釋或推論。
- 用於說明原理的假設、計算例子與建議測試。

不要把推論寫成官方結論，把示例寫成真實結果，或把有限驗證寫成全面保證。

只補充有證據支持的內容。材料不足時保留不確定性，不靠想像補齊數字、機制、測試過程或修復結果。

個別指標正常，只能支持其涵蓋範圍內的判斷。不能據此直接排除整個系統的問題；結果改善也不一定唯一證明某個原因。

### 規格與計算

涉及計算時，讀者應能追溯到「參數從哪裡來、採用什麼條件、如何代入、結果如何使用」。

公式需有可靠來源，或提供足以核對的推導。交代符號、單位、近似條件及適用範圍，不只列出一個結果。

每個關鍵輸入值都要說明身分：來自規格書、實測、指定設計條件，還是為解釋而採用的假設。假設值即使合理，也不能引用成規格書已提供的數值。

計算結果若只是起始估算，應說明後續如何量測或調整。不要把示例結果直接寫成所有產品都適用的推薦值。

區分標稱值、典型值、最大值、容差與不同測試條件。系列規格列出的多個選項，不代表某個具體料號同時具備全部選項。

不能僅憑同系列資料，認定某批料件的確定規格。需要時核對完整料號、訂購選項、版本與供應商確認資料。

若資料不足以從某個差值換算出另一項性能，就明確停在可計算的範圍，不補造缺少的參數。

### 引用、版本與匿名化

翻譯與資料整理尊重原文的論點、數字、條件、引用與重要限制；必要解說應與原文內容區分。

涉及時效性的資訊，核對適用日期或版本。來源版本有差異時，確認差異是否影響本文引用的內容，並在必要位置交代，不默默混用。

涉及個別測試時，說清楚測試對象、條件與範圍；無需每篇文章都附實測段落。使用者回報可以作為案例材料，但不能改寫成作者親自量測。

引用靠近相關內容，讓讀者知道它支持什麼。微信正文保留必要的完整可見網址，避免只有不可辨識的隱藏連結。

公開前移除密碼、金鑰、Token、私人訂閱網址、原始個資與其他不應公開的內容。檢查範圍包含正文、圖片、圖說、來源記錄及交付附件。

案例預設按科普所需程度匿名化，省略無關的專案名稱、內部版本、設備識別、熱點名稱與其他產品細節。公開品牌或型號若是分析對象、來源或理解所必需，可以保留。

匿名化不能破壞技術關係，也不能用虛構細節代替被刪除的資料。示意名稱與代號應保持一致，必要時說明其為通用示例。

## 五、封面與整體視覺

封面、標題、導入與正文應描述同一主題。封面標題可以比正文更短，保留必要關鍵詞，避免堆滿副標、日期與口號。

配色、字體層級與圖形語言在同篇文章內保持協調；不同題材可以使用不同風格，不把某一篇文章的色號或插畫形式固定成通用模板。

保持清楚、克制、有留白的呈現，讓視覺幫助理解。封面在常見顯示尺寸下仍須能辨識主題與標題，重要元素留出裁切空間。

每篇文章都必須提供合適的封面圖片。依主題生成新封面，或尋找有明確來源且適合使用的既有圖片；不能只提出封面構想而不交付圖片。

使用外部圖片時，保留來源及必要的使用條件說明。選圖與生成均需兼顧主題準確、視覺品質和正文風格。

封面作為獨立圖片檔案交付，便於直接上傳平台封面欄。需要不同尺寸時另行輸出，避免拉伸失真。

自製封面與圖解中的文字預設使用完整、自然、準確的英文。檢查拼字、大小寫、單位、公式與換行，不混入未要求的簡體中文，也不使用為了裝飾而堆砌的英文。

生成圖適合用於插畫或概念表達。不得把生成畫面偽裝成官方截圖、現場照片、產品實際介面、精確電路或測試證據。

## 六、配圖、圖表與原始截圖

圖文並茂以增加資訊價值為目的。每張圖應有明確作用，例如呈現對象、解釋關係、比較差異、展示資料或提供原始材料脈絡。

依內容選擇照片、插畫、流程圖、架構圖、數據圖表或截圖。不固定每篇的圖數，也不要求每篇都加入官方截圖。

當規格書、論文、標準或官方文件直接支持文章的關鍵判斷與計算時，應評估加入相關原始節選，讓讀者能對照原文；不以自製摘要圖完全取代必要的原始證據。

需要官方或原始截圖時，直接從真實來源取得，保留足夠脈絡，選擇與正文相關的部分。不重建、偽造或用生成圖模擬原始畫面。

原始截圖保留來源語言，包括原有的中英雙語或簡體中文，不為符合自製圖片的英文偏好而改寫原圖。解說放在繁體中文正文或圖說中。

裁切不能移除影響理解的欄名、單位、測試條件、註腳或版本資訊。需要遮蔽敏感資料時，不得連帶改變證據含義。

自製圖解可適度簡化，但方向、比例、連接、標註與條件不能造成誤解。精確技術圖優先採用可編輯、可核對的製圖方式，不依賴生成圖片保證公式、數字或連線正確。

數據圖表需讓數值、單位、範圍、比較條件與來源可辨識。沒有實測資料時，不用示意曲線或假想波形冒充量測結果。

圖說交代圖片在說明什麼；外部材料附來源，並區分原圖、自製示意、官方示例、生成概念圖與個別實測。

涉及規格節選時，正文應解釋與主題相關的欄位，以及它們如何參與判斷或計算。不要只放一張表格截圖，讓讀者自行猜測關聯。

圖片在正文實際顯示尺寸下應能閱讀。資訊過密時，可以分圖、另附原圖，或在正文提取關鍵參數，不把整頁密集資料縮成無法辨識的小圖。

有圖後可以精簡重複的示意框或描述，但保留理解所需的解釋。不要為增加圖片而堆疊相同資訊。

保留可用的原始圖片與適用的可編輯來源，便於平台補圖、修改和再利用。圖號、圖說、正文引用與圖片內容保持一致。

## 七、微信排版、交付與草稿操作

### HTML 排版與複製

預設交付完整 HTML 排版頁，供電腦瀏覽器一鍵複製富文字，貼進微信公眾號網頁正文編輯器；不只交原始碼、Markdown 或內容摘要。

正文使用適合微信的內嵌樣式，保持清楚的字級、行高、段距、標題層級與重點提示。避免依賴外部樣式、外部字型或正文腳本效果。

圖片適應正文欄並保留長寬比。長網址、表格或程式碼等特殊內容應避免橫向溢出。

表格不宜放入過多欄位或長篇文字。窄螢幕下若出現過度換行、欄位難以對照，應精簡表格或改用段落呈現。

HTML 排版頁必須提供兩個分開的按鈕：

1. **「一鍵複製正文」**：複製完整正文及配圖，保留適合平台的富文字排版；排除工具列、操作說明、狀態訊息、獨立封面及另行填寫的題目。
2. **「一鍵複製題目」**：只複製完整文章題目，方便直接貼入平台標題欄；不帶正文或其他說明。

兩個按鈕都屬必備交付，不能以手動選取、原始碼或檔案下載取代。正文剪貼簿提供富文字與純文字格式；題目使用純文字。另保留瀏覽器權限受限時的合理複製備援方式。

複製功能需實際驗證，不能只依賴按鈕顯示「成功」。核對剪貼簿或實際貼上結果是否包含完整內容、配圖與正確格式，並排除非正文介面。

保留圖片原檔，讓平台未接受內嵌圖片時仍可補入。不同平台可能調整部分格式，依實際驗證範圍描述相容性，不保證所有平台完全一致。

### 基本交付

基本交付必須同時包含：

1. **完整 HTML 排版頁**：具備兩個複製按鈕，可獨立開啟；正文樣式與圖片隨檔交付，避免依賴臨時預覽服務。
2. **可搬移的 Markdown 來源資料夾**：包含完整文章 Markdown、圖片子資料夾與簡短使用說明。正文配圖全部使用相對路徑，例如 `images/figure-01.png`；不使用本機絕對路徑、臨時網址或內嵌 Base64 取代圖片檔案。引用來源仍可使用正常網頁連結。
3. **可直接使用的獨立封面圖片**：交付原檔，並放入來源資料夾；封面不必重複插入正文。
4. **保留目錄結構的 ZIP 素材包**：內容與交付資料夾一致，便於下載、保存及轉交。

Markdown 與 HTML 保留相同題目、完整正文、圖說、引用與配圖內容；只允許呈現方式因格式而不同。Markdown 不保證重現微信富文字的所有視覺樣式。

來源資料夾整體搬移後，圖片仍須正常顯示。檔名依文章決定，不固化單篇題材；來源記錄、原始節選、可編輯圖源與驗證說明按實際內容補充。

製作流程宜維持單一正文來源，再產出不同格式。修訂時同步更新 HTML、Markdown、預覽與下載包，避免版本不同。

### 微信草稿操作

主要流程是電腦網頁編輯，不把手機操作設為必經步驟。

使用者要求貼入並保存草稿時，先確認目標文章及現有內容。保留使用者已在平台修改的題目、段落、圖說與設定，不直接以較舊的本地版本覆蓋。

若平台內容與本地來源不同，先比對差異，再將已確認的修改同步回正文來源與交付檔案。修訂限定在授權範圍內，不順便改動其他文章或設定。

保存後重新開啟或載入草稿，核對題目、完整正文、圖片順序、圖片載入、封面及相關欄位。僅看到編輯器中有內容，或按下保存按鈕，不足以宣稱保存成功。

沒有保存並重新開啟平台草稿時，不宣稱平台端持久化已驗證。保存草稿、預覽與正式發布是不同操作；只要求保存草稿時，不進行發布。

交付說明準確列出已完成與未驗證的範圍，不將平台預覽、草稿保存或本地檢查描述成正式發布或硬體實測驗收。

## 八、檢查與修訂

### 內容與證據

- [ ] 文章回答了明確問題，標題與內容一致，沒有超出證據的承諾。
- [ ] 全文完整、邏輯連貫、繁體用字與語氣自然。
- [ ] 段落、小標和圖文層級服務閱讀，沒有堆疊術語或過碎切分。
- [ ] 重要事實可追溯，規格、觀察、回報、推論與假設的邊界清楚。
- [ ] 計算的公式、參數來源、單位、假設與適用條件可以核對。
- [ ] 沒有將估算當成實裝值、將系列選項當成具體料號規格。
- [ ] 沒有將單項正常或一次改善，擴大成整體正常或唯一原因已證實。
